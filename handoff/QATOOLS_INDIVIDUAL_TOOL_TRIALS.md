# Individual tool trials and cook performance — 4 November 2026

This supersedes the new-HDA browser connection/tab workflow in QATOOLS_BROWSER_TRIAL_CONNECTION.md. Current UX: Get license key opens the account License Data page; Activate opens the existing masked key dialog with Activate/Refresh. No key is saved in HDA parameters or HIP files. The account connects once per assigned computer. Future tools reuse it.

## Per-tool behavior

- Updated runtime 5 requests signed protocol version 4. Account activation starts no individual tool trial. The legacy account-trial row remains for compatibility with older installers; it is not the v4 access decision.
- Placement/load of an unpurchased paid tool in the Houdini UI queues a background registration. Each account/product has one immutable 168-hour trial, created atomically on the first successful registration. The first tool already placed when the account is activated is registered then. Repeated nodes, reinstalls, new machines, cleared cache, key rotation and refunds do not reset that record.
- Different tools can start on different days. Bundles consist of these tools and do not have a second independent bundle timer. Projects require ownership as before. Published free and actively owned tools need no trial record. Ownership takes precedence over trial expiry; refunding ownership reveals the original trial state, not a fresh trial.
- Internet is required to register a new trial. Until a signed response arrives the tool says it is preparing its trial. Failed requests can be retried using Refresh inside Activate; trial requests never grant access offline based only on a local clock/file.
- At the next daily access check after expiry: “Your 7-day trial has ended. Purchase this tool to continue, then refresh or activate your license.” While a previously approved decision is still valid after the nominal trial end, the UI says “Trial active until next daily check”. Once blocked, the UI notice reads “Your 7-day trial has ended. Purchase this tool to continue.” Purchased/free tools hide the countdown and disable Purchase.
- The tab uses native fields in this order: email/machine/date, separator, State, spacer, Get license key, Activate, separator, trial countdown, spacer, expiry notice (when applicable), Purchase. The former blank headings, Start free trial button and extra purchase box are removed. Native green check/red cross indicators show state; expired Purchase has a green circle indicator. We do not modify Houdini's application stylesheet to tint a single button.
- New exports check runtime version 5 and report a direct update/restart instruction if old shared Python files are loaded. Re-exporting an HDA alone does not update Houdini's already loaded licensing module. The complete website installer contains qatools.json, HDA(s) and those shared Python files. Use update-local-runtime.ps1 and restart for local testing.

## Cook performance

The UI is not evaluated per geometry point. The existing Python SOP guard still has ordinary Houdini node scheduling/Python overhead when cooked. It now shares one verified in-memory proof per Houdini process. Signature verification/file-content reads happen only when the proof changes; a file metadata poll at most once per second detects changes made by other Houdini processes. Local writes/clear invalidate immediately. Cross-process cache changes can be noticed up to one second later. Successful per-tool access decisions are cached for up to 24 hours in the running process, bounded by the signed offline-license expiry. Each cook checks only that in-memory cache deadline. The next daily decision evaluates the original signed trial deadline; it never starts a fresh grace window for an already expired trial. Restarting forces a fresh decision. Activation, refresh, trial registration, signed denial and local clearing invalidate immediately; a changed file from another session also invalidates at the next metadata poll.

Normal cooking performs no HTTP, writes, scene scans, UI updates or trial registration. Background trial requests are serialized/coalesced by tool and credential; many copies do not produce many registrations. Their completion reaches the main thread through an idle callback, updates only affected node dependencies, and never calls node.cook(force=True). Explicit activation/refresh also updates dependencies without forcing every simulation to cook.

Measured in the agent's Windows Python environment: about 3 microseconds per warm client check across 10,000 checks (roughly 30 ms total), down from 6–7 microseconds with scope/expiry recomputed each time and about 454 microseconds when a metadata stat was done every time. This is illustrative, not a Houdini simulation benchmark or guaranteed latency. The verification suite repeats the benchmark on the owner's machine. Profile representative foreach/simulation networks in Houdini before making full-cook performance claims. Headless jobs must have their trials initialized in an interactive online session first; no network registration runs inside headless cooking.

## Security and transition

New table account_tool_trials has RLS and explicit revokes for browser and service direct access. Service-only RPCs verify confirmed account/current credential/current assignment, published tool identity and ownership. Trial requests use a signed machine-bound proof and rate limits; requests cannot select another account or change start/end timestamps. Projects and drafts cannot be trialed. v4 payloads carry independently signed per-tool dates. Existing v2/v3 license readers/endpoints remain for installer compatibility; new clients upgrade v3 renewal to v4, and new exports require runtime 5. No signing key or machine-ID change.

Existing account-wide trials cannot establish which tools someone actually used. Their records remain for legacy clients. A tool's first registration under the new per-tool system establishes its individual deadline; subsequent attempts cannot restart it. This is the one-time policy transition, not a reset of existing per-tool records.

## Rollout

1. Run scripts/verify-tool-trials.ps1 -Stage. It tests actual native HDA exports and builds the website, then stages only this batch plus the already prepared browser compatibility files it depends on. No deployment or migration is automatic.
2. supabase db push applies 20261104130000_individual_tool_trials.sql (and the previous browser migration if not yet applied). Commit/push after successful verification/migration and wait for Vercel Ready.
3. Run houdini/authoring/install-authoring.ps1 and houdini/authoring/update-local-runtime.ps1. Restart Houdini; do not hot-reload licensing modules in an active simulation.
4. Re-export the original editable development HDA for the new tab and callbacks. Replace its same-named ZIP in admin, Update product, and rebuild dependent bundles/projects. Download/install the fresh package. Website deployment does not rewrite stored customer ZIPs.
5. Activate once, place two unpurchased tools, and verify each receives a trial without another button click. Check free/purchased access and Purchase/Refresh behavior. Automated tests simulate expiry; do not change the operating-system clock or delete production trial records.

Agent checks include API/crypto tests, cross-language v4 signature verification, isolated PostgreSQL lifecycle tests (independent deadlines, no reset on repeated use/refund/release, free/project isolation and grants), Python cache/expiry tests, background request coalescing, and no forced cook tests. Native Houdini UI/export validation and production build require owner execution. The install page has a pre-existing Next Link lint finding unrelated to the trial copy.
